## 1. プロダクト原則(何のために作るか)

1. 【例: このプロダクトの第一価値は「総務の月次作業を30分にする」こと。迷ったらこれに寄与する方を選ぶ】
2. 【例: 対象ユーザーはITリテラシーの高くない中小企業の従業員。説明なしで使えないUIは作らない】
3. 【例: 今回のリリースで完璧を目指さない。MUSTを早く出して実ユーザーの声で直す】

## 2. スコープ原則(何をやらないか)

1. 【例: 給与計算・シフト管理・多言語対応はこのプロジェクトでは永久にやらない(別プロダクト)】
2. スコープの追加は必ず変更提案書経由。「ついで実装」は憲法違反
3. MUST機能は全機能の5割以下を維持する

## 3. 技術原則

1. 【例: スタックは TypeScript / Next.js / NestJS / PostgreSQL / AWS。変更は憲法改訂】
2. 3人で運用できない構成にしない(マイクロサービス・K8s禁止。マネージド最優先)
3. 【例: 全テーブルに company_id。テナント分離をアプリ層とテストで二重に保証する】
4. 正解が機械的に決まる検証はスクリプト(tools/)で行い、AIと人間は判断だけを行う

## 4. プロセス原則

1. コードより先にドキュメント。実装開始ゲート(check_gate.py + 人間チェック)を通らないものは実装しない
2. AIは起案者、人間が決定者。承認欄への記名なしに「承認済み」にしない。自己承認禁止
3. 決められないことは【未確定】として課題管理表へ。未確定のまま実装着手しない
4. 納期は常に3点予測(悲観/標準/楽観)で扱い、単一の日付を約束しない
5. 仕様変更は変更提案書 → 影響分析 → 「納期をずらす/他を削る/次に回す」の三択 → 文書改訂 → 実装の順

## 5. ドキュメント原則

1. docs/ が唯一の真実。チャット・口頭・Slackでの合意は docs/ に書かれるまで合意ではない
2. ID(F-/US-/SC-/API-)のトレーサビリティを常に維持する(check_traceability.py がNGの状態でマージしない)
3. 実装と設計書が乖離したら、見つけた人がその日のうちに課題を起票する
