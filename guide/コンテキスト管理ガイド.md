# コンテキスト管理ガイド — 「コンテキストがいっぱいです」を防ぐ

長いセッションでコンテキストが溢れる主因は、(1)コード・ドキュメントの全文読み込み、
(2)成果物のチャットへの全文出力、(3)1セッションに複数工程を詰め込むこと、の3つです。
このキットは以下の仕組みで対処します。

## 1. 仕組み: 調査サブエージェントへの委任

`agents/` に3つのサブエージェント定義があります。`.claude/agents/` に配置してください。

```bash
cp -r ai-upstream-kit/agents/* your-project/.claude/agents/
```

| エージェント | 役割 | 返すもの |
|---|---|---|
| `code-scout` | コードの調査(機能逆引き・暗黙仕様抽出・実装状況確認) | 出典つき要約 最大60行 |
| `doc-scout` | ドキュメントの調査(棚卸し・抜粋・ID整合チェック・矛盾検出) | 出典つき要約 最大50行 |
| `doc-reviewer` | ドキュメントレビュー(6観点+実装開始可否判定) | 指摘表のみ 最大25件 |

サブエージェントは**独立したコンテキスト**で動くため、彼らが何万行読んでも
メイン会話には要約しか入りません。各スキルには「調査は委任する」ルールを
組み込み済みなので、スラッシュコマンド経由なら自動的にこの動きになります。

長い調査結果は `docs/scout/` にファイルとして保存させ、メインには
「要約+パス」だけが返る運用です(必要になったときにピンポイントで読む)。

## 2. 仕組み: ファイル経由の工程間受け渡し

工程間の情報はチャット履歴ではなく **docs/ のファイルで受け渡し**ます。
各スキルは「成果物はファイルに書き、応答は要点15行+パスのみ」がルールです。

これの副作用として、**セッションを切っても失われるものがなくなります。**
「会話が切れてもdocs/だけで再開できる状態」が常に保たれているかが健全性の指標です。

## 3. 運用ルール: セッションの切り方

- **1工程=1セッション**を基本にする。`/req` が終わって承認したら、`/design` は
  新しいセッション(または `/clear` 後)で始める。前工程の内容は docs/ から
  doc-scout が取り出すので、会話履歴を引き継ぐ必要はない
- 工程の途中でコンテキストが厳しくなったら、「ここまでの確定事項と残作業を
  docs/wip/<工程名>_継続メモ.md に書き出して」と指示してから `/clear` し、
  再開時にそのメモを読ませる(`/compact` よりも確実で、何が残るかを自分で制御できる)
- 長時間のブレスト・雑談は設計セッションと分ける(混ぜると圧縮時に設計判断が失われがち)

## 4. 運用ルール: CLAUDE.md は「地図」にする

CLAUDE.md(プロジェクトのAI設定)に長文を書くと毎ターン読み込まれて逆効果です。
**中身ではなく在り処**を書きます:

```markdown
# ドキュメントの在り処(全文を読む前に doc-scout で必要箇所を特定すること)
- 要件: docs/01_要件定義書.md(機能一覧は§5.1)
- 設計: docs/03〜07(トレーサビリティ表は03の§2.1)
- バックログ正本: GitHub Issues(俯瞰は docs/backlog/product_backlog.md)
- 課題: docs/issues/課題管理表.md
# ルール
- 調査は code-scout / doc-scout に委任。成果物はdocs/に保存しチャットに全文を出さない
```

## 5. どこまで委任するかの目安

| 状況 | 推奨 |
|---|---|
| 3ファイル以上読む調査 | 必ず委任 |
| 編集対象ファイルを1〜2個読む | 自分で読んでよい |
| 委任結果で特定された箇所の確認(数十行) | 自分で読んでよい |
| ドキュメント全文レビュー | doc-reviewer に委任 |
| 「リポジトリ全体を把握したい」 | code-scout に委任し、結果を docs/scout/ に保存させる |

※サブエージェントは会話できない使い切りの調査員なので、「何を・どの形式で返すか」を
  具体的に指示するほど精度が上がります(各スキルの委任指示はその形になっています)。
