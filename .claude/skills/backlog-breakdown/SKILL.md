# バックログ分解・見積りスキル

要件定義書(最低でも機能一覧+ユーザーストーリー)をインプットに、
スクラムのプロダクトバックログを作成する。テンプレートは `templates/12_プロダクトバックログ.md`。

## 前提条件
- 要件定義書があること。なければ `requirements-definition` スキルを先に提案する。
  ただし「大まかな洗い出しだけ先にしたい」という依頼なら、ストーリーメモだけからドラフト版を作ってよい
  (その場合、全項目に【要件未確定】マークを付ける)。
- DoR/DoD(`templates/15_DoR_DoD.md`)が未定義なら、ドラフトを一緒に提案する。

## 分解の階層

```
エピック(E-xx)      = 機能のかたまり。要件定義書の機能グループに対応
 └ ストーリー(US-xxx) = 1スプリントで完了できる、ユーザー価値の単位
    └ タスク(T-xxx)   = 実装作業の単位(0.5〜2人日目安)。スプリント計画時に詳細化
```

## 進め方

### Step 1: エピック分解
要件定義書の機能一覧(F-xxx)をエピックにグルーピングする。
機能IDとの対応表を必ず作る(F-xxxがどのエピックにも属さない=漏れ)。

### Step 2: ストーリー分解
各エピックを INVEST 原則でストーリーに分解する:
- 形式: 「<ロール>として、<目的>のために、<機能>がほしい」
- **1ストーリーは1スプリント(2週間)で完了できるサイズまで割る。**
  8SPを超える見込みのものは分割する(分割パターン: CRUD別 / ロール別 / 正常系→異常系 / 手動→自動)
- 各ストーリーに**受入条件(Acceptance Criteria)を3〜7個**、Given/When/Then形式で書く
- 機能ストーリーだけでなく以下も必ず起票する(忘れるとベロシティが嘘になる):
  - 技術基盤ストーリー(環境構築、CI/CD、認証基盤など)→ Sprint 0〜1 に配置
  - スパイク(技術調査。タイムボックスを人日で明記)
  - 非機能ストーリー(性能対策、監視設定、セキュリティ対応)

### Step 3: ストーリーポイント見積り(AI案)
- フィボナッチ(1, 2, 3, 5, 8, 13)で相対見積りする
- まず**基準ストーリー**を1つ選び「これを3SP」と宣言し、他は比較で付ける
- 各見積りに理由を1行付ける(複雑度/不確実性/作業量の内訳)
- 13SPが付いたストーリーは自動的に分割対象としてフラグを立てる
- **AIの見積りはあくまでプランニングポーカーの叩き台。** 出力に
  「チームでポーカーを実施し、AI案と2段階以上ズレたものは理由を議論して上書きすること」と明記する

### Step 4: 優先順位付け(案)
以下の合成で並び順の案を作り、PO判断用のメモを付ける:
- 要件定義書の MUST/SHOULD/COULD
- 依存関係(技術基盤が先、他ストーリーをブロックするものが先)
- リスク(不確実性の高いものは早いスプリントで検証)

### Step 5: 出力
1. `docs/backlog/product_backlog.md`(テンプレート12準拠の一覧表)
2. GitHub Issues 一括登録用の `gh` CLIスクリプト(`docs/backlog/create_issues.sh`):
   - エピック=ラベル `epic:E-xx`、SP=ラベル `sp:5`、優先順位=マイルストーン or Projectsフィールド
   - 受入条件はIssue本文のチェックリストにする
   - 実行前にdry-run表示すること
3. サマリ: 総SP、エピック別SP、リスクフラグ付きストーリー一覧

### Step 6: セルフレビュー
- [ ] 全機能ID(F-xxx)がいずれかのストーリーにトレースできる
- [ ] 全ストーリーに受入条件がある(「〜できること」だけの曖昧な条件はNG)
- [ ] 技術基盤・スパイク・非機能のストーリーが含まれている
- [ ] 13SP超や「1スプリントに収まらない」ストーリーが残っていない
- [ ] 見積りの分布が不自然でない(全部3SPなど相対見積りになっていないケース)

## 次工程
総SPが出たら `release-planning` スキルで納期予測へ。

## コンテキスト管理(必須)

- **調査は委任する。** 既存コードの読み込みは `code-scout`、既存ドキュメントの読み込み・整合チェックは
  `doc-scout` サブエージェントに委任し、要約(出典つき)だけを受け取る。
  自分でReadしてよいのは「これから編集するファイル」と「委任結果で特定された数箇所の確認」のみ。
- **インプットは全文引用しない。** 参照は「ドキュメントID §セクション」で行う。
  必要な抜粋(機能一覧表など)だけをdoc-scoutに抽出させる。
- **成果物はファイルに書き、チャットには出さない。** docs/ に保存し、応答は
  「要点サマリ(15行以内)+保存パス+レビューしてほしい箇所」のみ。
- **レビューは `doc-reviewer` サブエージェントに委任**し、指摘表だけ受け取る。
- 長い工程の途中では、確定事項を docs/ 側に書き出してから次に進む
  (会話が切れても docs/ だけで再開できる状態を常に保つ)。

## ロジック委譲・チェックポイント(必須)

**AIでやらないこと(tools/のスクリプトを実行して結果だけ読む):**
- ID整合チェック: `python3 tools/check_traceability.py docs`(表の突き合わせを自分でやらない)
- Mermaid検証: `python3 tools/validate_mermaid.py docs`
- 納期・ベロシティ計算: `python3 tools/forecast.py ...`(計算はスクリプト、AIは入力値の決定と解釈のみ)
- ゲート判定: `python3 tools/check_gate.py`

**中断・再開プロトコル(コンテキスト切れ・停止への備え):**
1. 開始時: `python3 tools/pipeline.py status` を実行。この工程(backlog)が in_progress で
   docs/wip/ に継続メモがあれば、**最初からやり直さず**メモの「次の1手」から再開する
2. 開始宣言: `python3 tools/pipeline.py start backlog`
3. 主要Step完了ごとに: 成果物をdocsに保存 → `python3 tools/pipeline.py step backlog "StepN完了"` →
   docs/wip/backlog_継続メモ.md を上書き(済みStep / 確定事項 / 未解決の論点 / 次の1手 を各3行以内)
4. 完了時: `python3 tools/pipeline.py done backlog` を実行し、継続メモを削除する

この手順により、途中でセッションが止まっても /resume で数秒で復帰できる。

## 憲法の遵守(必須)

開始時に `docs/00_プロジェクト憲法.md` が存在すれば必ず読み、全出力をその原則に従わせる
(短い1ページなのでこれは自分で読んでよい)。憲法と矛盾する指示・要望を受けたら、
黙って従わず「憲法§Xと矛盾するため、先に憲法改訂(変更提案書=/change)が必要」と指摘する。
憲法が存在しない場合は、要件定義の完了時に templates/00 からドラフトを作ることを提案する。
