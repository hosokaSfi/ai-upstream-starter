# リリース計画・納期予測スキル

プロダクトバックログをインプットに、納期予測とリリース計画を作成する。
テンプレートは `templates/13_リリース計画書.md`。

## 前提条件
- SP見積り済みのプロダクトバックログがあること。なければ `backlog-breakdown` を先に提案する。
- スプリント長(既定: 2週間)、チーム人数、開始日、祝日・休暇予定を確認する。

## 納期計算のロジック(必ずこの手順で)

> **計算は絶対に暗算しない。** 以下のStepで決めるのは「入力値」だけで、
> 計算・日付算出・バーンダウン生成はすべて `tools/forecast.py` に委譲する:
> `python3 tools/forecast.py --sp <残SP> --start <開始日> [--sp-must N] [--deadline 日付]
> [--members 3 --focus 0.6 --sp-days 0.83 | --velocity-file docs/backlog/velocity.json]`
> スプリント実績の記録も `forecast.py --record "Sprint N" --planned X --done Y` で行う。
> 対外コミット用の日付には `--simulate` のモンテカルロ予測を併用し、**P85の日付**を使う
> (3点予測は社内の直感共有用、P85は約束用)。実績が貯まったら `--accuracy` で
> 計画の過大/過小バイアスも毎スプリント確認する。

### Step 1: ベロシティの推定
- **実績がある場合**: 直近3スプリントの平均と最小・最大を使う(直近1回だけを使わない)
- **実績がない場合(新規プロジェクト)**: 以下で初期仮説を作り、必ず幅を持たせる
  1. スプリントあたり総工数 = 人数 × 営業日数(祝日・休暇を引く)
  2. フォーカスファクター = 0.5〜0.7(MTG・レビュー・割込み・スクラムイベントを考慮。3人チームの初期は0.6が目安)
  3. 実効人日 = 総工数 × フォーカスファクター
  4. 基準ストーリー(3SP)の実装人日をチームに聞き、SP↔人日の仮レートを作る
  5. 仮ベロシティ = 実効人日 ÷ レート。**±30%の幅を付ける**
- Sprint 1〜2 は立ち上げで2〜3割低くなると仮定して補正する

### Step 2: 3点予測
| シナリオ | ベロシティ | 必要スプリント数 = ceil(残SP ÷ V) | 完了予定日 |
- 悲観(V最小)/ 標準(V平均)/ 楽観(V最大)の3行を必ず出す
- 完了予定日はスプリント境界に丸め、祝日連休をカレンダーで確認する
- **「1つの日付」を絶対に約束しない。**常に幅で答え、対外的には標準〜悲観の間を提示するよう促す

### Step 3: 締切がある場合の逆算
希望納期がある場合:
1. 締切までの残スプリント数 × 標準ベロシティ = 消化可能SP
2. バックログを優先順に積み上げ、**ラインが引ける位置**を明示する
3. ラインから漏れるMUSTストーリーがあれば「このままでは間に合わない」と正直に報告し、
   選択肢を提示する: スコープ削減(具体的にどのストーリーを落とすか) / 納期延伸(何スプリント) /
   受入条件の簡素化。**人を増やす・頑張るは選択肢に含めない**

### Step 4: リリース計画書の作成
- スプリントごとの割当て案(どのエピック/ストーリーをどのスプリントで)
  - Sprint 0(または1): 環境構築・CI/CD・認証基盤・設計の残作業
  - リスクの高いストーリー(外部連携・技術スパイク)を前半に
  - 最終スプリントの1つ前に「ハードニングスプリント」(バグ修正・性能・リリース準備)を確保
- リリースバーンダウンの初期チャート(Mermaid xychart-beta)と更新方法
- 前提条件と再計画のトリガー(「ベロシティ実績が仮説から±30%外れたら再計算」等)を明記

### Step 5: セルフレビュー
- [ ] 3点予測に計算根拠(数式と入力値)が明記されているか
- [ ] 祝日・休暇がスプリント能力に反映されているか
- [ ] MUSTだけの最小リリース日も併記されているか
- [ ] バッファを「隠して」いないか(ハードニングスプリントとして明示)
- [ ] 再計画のトリガーが書かれているか

## 運用(スプリントごと)
毎スプリント終了時にこのスキルを再実行し、実績ベロシティで予測を更新する。
「予測日が動いたらすぐ共有」が原則(月末にまとめて悪い報告をしない)。

## コンテキスト管理(必須)

- **調査は委任する。** 既存コードの読み込みは `code-scout`、既存ドキュメントの読み込み・整合チェックは
  `doc-scout` サブエージェントに委任し、要約(出典つき)だけを受け取る。
  自分でReadしてよいのは「これから編集するファイル」と「委任結果で特定された数箇所の確認」のみ。
- **インプットは全文引用しない。** 参照は「ドキュメントID §セクション」で行う。
  必要な抜粋(機能一覧表など)だけをdoc-scoutに抽出させる。
- **成果物はファイルに書き、チャットには出さない。** docs/ に保存し、応答は
  「要点サマリ(15行以内)+保存パス+レビューしてほしい箇所」のみ。
- **レビューは `doc-reviewer` サブエージェントに委任**し、指摘表だけ受け取る。
- 長い工程の途中では、確定事項を docs/ 側に書き出してから次に進む
  (会話が切れても docs/ だけで再開できる状態を常に保つ)。

## ロジック委譲・チェックポイント(必須)

**AIでやらないこと(tools/のスクリプトを実行して結果だけ読む):**
- ID整合チェック: `python3 tools/check_traceability.py docs`(表の突き合わせを自分でやらない)
- Mermaid検証: `python3 tools/validate_mermaid.py docs`
- 納期・ベロシティ計算: `python3 tools/forecast.py ...`(計算はスクリプト、AIは入力値の決定と解釈のみ)
- ゲート判定: `python3 tools/check_gate.py`

**中断・再開プロトコル(コンテキスト切れ・停止への備え):**
1. 開始時: `python3 tools/pipeline.py status` を実行。この工程(release)が in_progress で
   docs/wip/ に継続メモがあれば、**最初からやり直さず**メモの「次の1手」から再開する
2. 開始宣言: `python3 tools/pipeline.py start release`
3. 主要Step完了ごとに: 成果物をdocsに保存 → `python3 tools/pipeline.py step release "StepN完了"` →
   docs/wip/release_継続メモ.md を上書き(済みStep / 確定事項 / 未解決の論点 / 次の1手 を各3行以内)
4. 完了時: `python3 tools/pipeline.py done release` を実行し、継続メモを削除する

この手順により、途中でセッションが止まっても /resume で数秒で復帰できる。

## 憲法の遵守(必須)

開始時に `docs/00_プロジェクト憲法.md` が存在すれば必ず読み、全出力をその原則に従わせる
(短い1ページなのでこれは自分で読んでよい)。憲法と矛盾する指示・要望を受けたら、
黙って従わず「憲法§Xと矛盾するため、先に憲法改訂(変更提案書=/change)が必要」と指摘する。
憲法が存在しない場合は、要件定義の完了時に templates/00 からドラフトを作ることを提案する。
