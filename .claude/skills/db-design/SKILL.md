# DB設計スキル

要件定義書・基本設計書をインプットとして、ER図(Mermaid)、テーブル定義書、DDL(SQL)を作成する。
テンプレートは `templates/06_DB設計書_ER図.md`。

## 前提条件の確認
- 要件定義書(最低限、機能一覧とユーザーストーリー)があること。なければ中断して提案。
- 基本設計書があれば画面項目からカラムを逆引きできるため精度が上がる。
  なければ「基本設計と並行で進め、画面設計確定後にカラムを見直す」ことを明示する。
- RDBMSの種類(PostgreSQL / MySQL / その他)を確認する。未定ならPostgreSQLを推奨し【仮】とする。

## 進め方

### Step 1: エンティティ抽出
- 要件定義書の名詞を洗い出してエンティティ候補にする(ユーザー、申請、承認、通知…)
- マスタ系 / トランザクション系 / 履歴・ログ系 に分類する
- 「登録する・一覧で見る・検索する」対象は必ずテーブルになる

### Step 2: ER図の作成(Mermaid erDiagram)
- リレーションはカーディナリティ(`||--o{` 等)を正しく書く
- 多対多は必ず中間テーブルに分解する
- 図が大きくなる場合はサブシステム単位で図を分割し、全体俯瞰図(エンティティ名のみ)を別に置く

### Step 3: テーブル定義書
テーブルごとに以下の表を作る:
| カラム名 | 論理名 | 型 | NULL | デフォルト | 制約・説明 |

必ず適用する設計標準(プロジェクト側で上書き可):
- 命名: テーブルは複数形スネークケース(`users`, `leave_requests`)、カラムはスネークケース
- 全テーブル共通カラム: `id`(PK, bigint or UUID — どちらかに統一)、`created_at`、`updated_at`
- 論理削除を使う場合は `deleted_at`(timestamp, NULL可)で統一し、ユニーク制約との相互作用を明記
- 外部キーには必ずインデックス。検索条件になるカラムもインデックス候補として列挙
- ENUMは原則使わず、チェック制約 or 参照マスタテーブル(理由も記載)
- 金額は `numeric`、日時は `timestamptz`(UTC保存・表示時変換)

### Step 4: 主要クエリの検証
主要画面(一覧・検索・ダッシュボード)ごとに「発行されるであろうSQL」を書き、
- N+1が起きない構造か
- インデックスが効くか
- 件数が増えたとき(1年後の想定件数)に破綻しないか
を検証する。想定件数はテーブルごとに「初期件数 / 1年後件数」を見積もって表にする。

### Step 5: DDL生成
CREATE TABLE文一式を生成する。マイグレーションツール(Prisma / Flyway / Rails等)が
決まっている場合はその形式でも出力する。

### Step 6: セルフレビュー
- [ ] 基本設計書の全画面・全APIが、参照するテーブルを持っている(トレーサビリティ)
- [ ] 全ユーザーストーリーがER図上で実現可能か(データの置き場がないストーリーがないか)
- [ ] 履歴要件(「変更履歴を見たい」等)に対応する履歴テーブルがあるか
- [ ] 一意性制約の漏れ(メールアドレス重複登録など)がないか
- [ ] Mermaid erDiagramが構文エラーなくレンダリングされるか
- [ ] DDLが実際にRDBMSで実行可能か(可能なら実際にDocker等で流して検証する)

## 禁止事項
- ER図だけ書いてテーブル定義書(型・制約)を省略すること
- 「とりあえずJSON型カラム」で設計から逃げること(使う場合は理由と検索要件を明記)
- インデックス設計を「実装時に考える」とすること

## コンテキスト管理(必須)

- **調査は委任する。** 既存コードの読み込みは `code-scout`、既存ドキュメントの読み込み・整合チェックは
  `doc-scout` サブエージェントに委任し、要約(出典つき)だけを受け取る。
  自分でReadしてよいのは「これから編集するファイル」と「委任結果で特定された数箇所の確認」のみ。
- **インプットは全文引用しない。** 参照は「ドキュメントID §セクション」で行う。
  必要な抜粋(機能一覧表など)だけをdoc-scoutに抽出させる。
- **成果物はファイルに書き、チャットには出さない。** docs/ に保存し、応答は
  「要点サマリ(15行以内)+保存パス+レビューしてほしい箇所」のみ。
- **レビューは `doc-reviewer` サブエージェントに委任**し、指摘表だけ受け取る。
- 長い工程の途中では、確定事項を docs/ 側に書き出してから次に進む
  (会話が切れても docs/ だけで再開できる状態を常に保つ)。

## ロジック委譲・チェックポイント(必須)

**AIでやらないこと(tools/のスクリプトを実行して結果だけ読む):**
- ID整合チェック: `python3 tools/check_traceability.py docs`(表の突き合わせを自分でやらない)
- Mermaid検証: `python3 tools/validate_mermaid.py docs`
- 納期・ベロシティ計算: `python3 tools/forecast.py ...`(計算はスクリプト、AIは入力値の決定と解釈のみ)
- ゲート判定: `python3 tools/check_gate.py`

**中断・再開プロトコル(コンテキスト切れ・停止への備え):**
1. 開始時: `python3 tools/pipeline.py status` を実行。この工程(db)が in_progress で
   docs/wip/ に継続メモがあれば、**最初からやり直さず**メモの「次の1手」から再開する
2. 開始宣言: `python3 tools/pipeline.py start db`
3. 主要Step完了ごとに: 成果物をdocsに保存 → `python3 tools/pipeline.py step db "StepN完了"` →
   docs/wip/db_継続メモ.md を上書き(済みStep / 確定事項 / 未解決の論点 / 次の1手 を各3行以内)
4. 完了時: `python3 tools/pipeline.py done db` を実行し、継続メモを削除する

この手順により、途中でセッションが止まっても /resume で数秒で復帰できる。

## 憲法の遵守(必須)

開始時に `docs/00_プロジェクト憲法.md` が存在すれば必ず読み、全出力をその原則に従わせる
(短い1ページなのでこれは自分で読んでよい)。憲法と矛盾する指示・要望を受けたら、
黙って従わず「憲法§Xと矛盾するため、先に憲法改訂(変更提案書=/change)が必要」と指摘する。
憲法が存在しない場合は、要件定義の完了時に templates/00 からドラフトを作ることを提案する。
