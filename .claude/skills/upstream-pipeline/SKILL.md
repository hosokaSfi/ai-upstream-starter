# 上流工程パイプライン(オーケストレーター)

上流工程のドキュメント一式を、正しい順序・承認ゲートつきで作成する。
個別工程の詳細手順は各スキル(requirements-definition / basic-design / db-design / architecture-design)に従う。

## パイプライン全体像(スクラム版)

```
Phase 1: 要件定義      → 01_要件定義書, 02_非機能要件定義書     【承認ゲート1】
Phase 2: 基本設計      → 03_基本設計書, 04_画面設計書, 05_API仕様書 【承認ゲート2】
Phase 3: データ/基盤   → 06_DB設計書_ER図, 07_アーキテクチャ設計書  【承認ゲート3】
Phase 4: 計画          → 12_プロダクトバックログ(backlog-breakdownスキル),
                         13_リリース計画書=納期予測(release-planningスキル),
                         15_DoR_DoD, 08_テスト計画書, 10_運用設計書 【最終承認】
```

- Phase 4 は従来型(ウォーターフォール寄り)の場合のみ `09_WBS_開発計画書` を使う。
  スクラム運用ではWBSの代わりにプロダクトバックログ+リリース計画書が計画成果物となる。
- Phase 2〜3 は「Sprint 0 で最初のインクリメントに必要な範囲だけ承認し、
  以降はスプリントと並走してリファインメントで詳細化する」進め方を許容する
  (その場合、未詳細化の範囲を基本設計書に【リファインメントで詳細化】と明記する)。

## 実行ルール

1. **開始時に現状診断を行う。** 既存のドキュメント・コード・ストーリーを確認し、
   「どのPhaseから始めるべきか」「既存資産のどこに欠落があるか」を診断レポートとして提示してから始める。
   (例: 途中まで開発が進んでいる場合、コードから現状仕様を逆引きして要件定義書に反映する)

2. **承認ゲートでは必ず停止する。** 各Phaseの成果物を提示し、ユーザーの承認を得てから
   次のPhaseに進む。承認前に次Phaseを先行生成しない(手戻りの温床になるため)。
   ユーザーが「全部一気に」と明示した場合のみ、各成果物に【未承認ドラフト】と明記して連続生成する。

3. **成果物は `docs/` フォルダに番号順で保存する。**
   ```
   docs/
   ├── 01_要件定義書.md
   ├── 02_非機能要件定義書.md
   ├── ...
   └── issues/課題管理表.md
   ```

4. **課題管理表を常に更新する。** 各工程で出た【未確定】項目は
   `docs/issues/課題管理表.md` に「No / 起票日 / 内容 / 決定者 / 期限 / ステータス」で追記する。

5. **整合性チェックを各Phase末に実行する。**
   - Phase 2末: 全機能ID(F-xxx)が画面ID/API IDに紐づくか
   - Phase 3末: 全画面・APIが参照テーブルを持つか、非機能要件が構成に反映されているか
   - Phase 4末: WBSの全タスクが機能IDに紐づくか、見積り合計と納期が整合するか
   不整合はリストにして修正してからゲートに出す。

6. **各ドキュメント冒頭に管理ヘッダを付ける。**
   ```markdown
   | 項目 | 内容 |
   |---|---|
   | ドキュメントID | REQ-001 |
   | バージョン | 0.1 (ドラフト) |
   | 作成 | Claude (AI) |
   | レビュー担当 | 【記入待ち】 |
   | 承認者 / 承認日 | 【記入待ち】 |
   | ステータス | ドラフト / レビュー中 / 承認済み |
   ```

## Phase 4 の成果物

### 12 プロダクトバックログ(→ backlog-breakdown スキル)
- エピック→ストーリー→(タスク)分解、受入条件、SP見積り案、GitHub Issues登録スクリプト

### 13 リリース計画書(→ release-planning スキル)
- ベロシティ仮説と3点予測(悲観/標準/楽観)による納期計算
- スプリント割当て案(Sprint 0=基盤、リスク高を前半、ハードニングを終盤)
- **消化可能SPが希望納期に収まらない場合、正直に報告し、スコープ削減案を提示する**

### 15 DoR / DoD
- Ready の定義(このゲート自体がDoRの土台になる)と Done の定義

### 08 テスト計画書
- テストレベルごとの範囲・担当・完了基準(DoDと整合させる)
- 機能ID×テストレベルのマトリクス(=テスト漏れ検知)

### 10 運用設計書
- リリース手順、障害対応フロー、バックアップ/リストア手順、定期運用作業一覧

### (従来型の場合のみ)09 WBS・開発計画書
- 機能ID単位でタスク分解(1タスク3人日以内)、クリティカルパス、明示バッファ20%

## 完了条件
README記載の「実装開始ゲートチェックリスト」を全項目確認し、結果を最終レポートとして提出する。

## コンテキスト管理(必須)

- **調査は委任する。** 既存コードの読み込みは `code-scout`、既存ドキュメントの読み込み・整合チェックは
  `doc-scout` サブエージェントに委任し、要約(出典つき)だけを受け取る。
  自分でReadしてよいのは「これから編集するファイル」と「委任結果で特定された数箇所の確認」のみ。
- **インプットは全文引用しない。** 参照は「ドキュメントID §セクション」で行う。
  必要な抜粋(機能一覧表など)だけをdoc-scoutに抽出させる。
- **成果物はファイルに書き、チャットには出さない。** docs/ に保存し、応答は
  「要点サマリ(15行以内)+保存パス+レビューしてほしい箇所」のみ。
- **レビューは `doc-reviewer` サブエージェントに委任**し、指摘表だけ受け取る。
- 長い工程の途中では、確定事項を docs/ 側に書き出してから次に進む
  (会話が切れても docs/ だけで再開できる状態を常に保つ)。

## ロジック委譲・チェックポイント(必須)

**AIでやらないこと(tools/のスクリプトを実行して結果だけ読む):**
- ID整合チェック: `python3 tools/check_traceability.py docs`(表の突き合わせを自分でやらない)
- Mermaid検証: `python3 tools/validate_mermaid.py docs`
- 納期・ベロシティ計算: `python3 tools/forecast.py ...`(計算はスクリプト、AIは入力値の決定と解釈のみ)
- ゲート判定: `python3 tools/check_gate.py`

**中断・再開プロトコル(オーケストレーターの場合):**
- パイプライン自体の状態は持たない。**各Phaseの工程名(req / design / db / arch / backlog / release)**で
  `pipeline.py start/step/done` を実行し、個々のスキルの再開プロトコルに従わせる
- 開始時は必ず `python3 tools/pipeline.py status` で「次の一手」を確認し、
  in_progress の工程があればその継続メモから再開する(最初のPhaseからやり直さない)

この手順により、途中でセッションが止まっても /resume で数秒で復帰できる。

## 憲法の遵守(必須)

開始時に `docs/00_プロジェクト憲法.md` が存在すれば必ず読み、全出力をその原則に従わせる
(短い1ページなのでこれは自分で読んでよい)。憲法と矛盾する指示・要望を受けたら、
黙って従わず「憲法§Xと矛盾するため、先に憲法改訂(変更提案書=/change)が必要」と指摘する。
憲法が存在しない場合は、要件定義の完了時に templates/00 からドラフトを作ることを提案する。
