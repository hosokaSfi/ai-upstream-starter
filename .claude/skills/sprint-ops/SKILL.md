# スプリント運営スキル

スクラムイベントごとのAI支援をまとめたスキル。使う場面に応じて該当セクションだけ実行する。

## 1. スプリント計画(スプリント開始日)

インプット: プロダクトバックログ(優先順)、前スプリントの実績ベロシティ、チームの今スプリントの稼働(休暇等)

1. キャパシティ計算: 実績ベロシティ × 稼働補正(休暇日数分を減らす)
2. 優先順位の上からキャパシティに収まる分のストーリーを候補として提示
3. **スプリントゴールを1文で提案**(ストーリーの寄せ集めではなく「このスプリントが終わると何ができるか」)
4. 各ストーリーをタスク(T-xxx)に分解する:
   - 粒度: 0.5〜2人日。2人日超は分割
   - 実装だけでなく「テスト作成」「レビュー対応」「ドキュメント更新(設計書の該当節)」を必ず含める
   - 分解結果はテンプレート `templates/14_スプリント計画書.md` に出力
   - GitHub Issues運用の場合、ストーリーIssueのチェックリスト(タスクリスト)として追記するghコマンドを生成
5. DoR(`templates/15_DoR_DoD.md`)を満たさないストーリーが混ざっていたら警告する

## 2. バックログリファインメント(スプリント中盤・週1回30分)

1. 次スプリント候補のストーリー(優先順位上位、ベロシティの1.5倍分)を対象に:
   - 受入条件の曖昧さを指摘し、Given/When/Thenに書き直す
   - 設計書(基本設計・DB設計)との不整合を検出する(新テーブルが必要なのにDB設計書に無い等)
   - 8SP超のストーリーの分割案を出す
2. 新しく積まれた要望を既存バックログと突き合わせ、重複・矛盾・優先順位案を提示する
   (→ 変更管理は `guide/スクラム運用ガイド.md` §4 のルールに従う)

## 3. スプリントレビュー資料(スプリント最終日)

1. 完了ストーリー一覧(受入条件の達成状況つき)と未完了の持ち越し理由
2. デモ手順書(何をどの順に見せるか、デモ用データ)
3. ステークホルダー向けサマリ(1ページ: 今回できたこと/次回予定/納期予測の最新値)

## 4. レトロスペクティブ(スプリント最終日)

1. 実績データの整理: 計画SP vs 完了SP、持ち越し率、割込み作業の件数
2. チームが出したKeep/Problemの生メモを、パターン別に整理して提示
3. Tryの候補を提案する(ただし**Tryは1スプリント1〜2個まで**に絞らせる)
4. ベロシティ実績を `docs/backlog/velocity.md` に追記し、
   `release-planning` スキルでの納期予測更新を促す

## 5. デイリースクラム支援(任意)

GitHub Issues / PRの直近24時間の動きから、デイリー用の状況サマリを生成する
(完了・進行中・ブロック中の一覧)。デイリーそのものの代替ではなく、事前の情報整理として使う。

## 禁止事項
- チームの合意なくスプリントゴールやSPを確定扱いにすること(常に「案」として出す)
- 未完了ストーリーのSPを部分計上すること(完了の定義を満たさないものは0)
- レトロで個人を名指しした批判を生成すること(プロセスの問題として書く)

## コンテキスト管理(必須)

- **調査は委任する。** 既存コードの読み込みは `code-scout`、既存ドキュメントの読み込み・整合チェックは
  `doc-scout` サブエージェントに委任し、要約(出典つき)だけを受け取る。
  自分でReadしてよいのは「これから編集するファイル」と「委任結果で特定された数箇所の確認」のみ。
- **インプットは全文引用しない。** 参照は「ドキュメントID §セクション」で行う。
  必要な抜粋(機能一覧表など)だけをdoc-scoutに抽出させる。
- **成果物はファイルに書き、チャットには出さない。** docs/ に保存し、応答は
  「要点サマリ(15行以内)+保存パス+レビューしてほしい箇所」のみ。
- **レビューは `doc-reviewer` サブエージェントに委任**し、指摘表だけ受け取る。
- 長い工程の途中では、確定事項を docs/ 側に書き出してから次に進む
  (会話が切れても docs/ だけで再開できる状態を常に保つ)。

## ロジック委譲・チェックポイント(必須)

**AIでやらないこと(tools/のスクリプトを実行して結果だけ読む):**
- ID整合チェック: `python3 tools/check_traceability.py docs`(表の突き合わせを自分でやらない)
- Mermaid検証: `python3 tools/validate_mermaid.py docs`
- 納期・ベロシティ計算: `python3 tools/forecast.py ...`(計算はスクリプト、AIは入力値の決定と解釈のみ)
- ゲート判定: `python3 tools/check_gate.py`

**中断・再開プロトコル(コンテキスト切れ・停止への備え):**
1. 開始時: `python3 tools/pipeline.py status` を実行。この工程(sprint)が in_progress で
   docs/wip/ に継続メモがあれば、**最初からやり直さず**メモの「次の1手」から再開する
2. 開始宣言: `python3 tools/pipeline.py start sprint`
3. 主要Step完了ごとに: 成果物をdocsに保存 → `python3 tools/pipeline.py step sprint "StepN完了"` →
   docs/wip/sprint_継続メモ.md を上書き(済みStep / 確定事項 / 未解決の論点 / 次の1手 を各3行以内)
4. 完了時: `python3 tools/pipeline.py done sprint` を実行し、継続メモを削除する

この手順により、途中でセッションが止まっても /resume で数秒で復帰できる。

## 憲法の遵守(必須)

開始時に `docs/00_プロジェクト憲法.md` が存在すれば必ず読み、全出力をその原則に従わせる
(短い1ページなのでこれは自分で読んでよい)。憲法と矛盾する指示・要望を受けたら、
黙って従わず「憲法§Xと矛盾するため、先に憲法改訂(変更提案書=/change)が必要」と指摘する。
憲法が存在しない場合は、要件定義の完了時に templates/00 からドラフトを作ることを提案する。
