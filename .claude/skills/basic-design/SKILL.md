# 基本設計スキル

承認済みの要件定義書をインプットとして、基本設計書・画面設計書・API仕様書を作成する。
テンプレートは `templates/03_基本設計書.md`、`templates/04_画面設計書.md`、`templates/05_API仕様書.md`。

## 前提条件の確認(スキップ禁止)

開始前に必ず確認する:
1. **要件定義書が存在し、承認済みか。** 存在しない場合はこの工程を中断し、
   先に `requirements-definition` スキルの実行を提案する。
2. 要件定義書に【未確定】のMUST機能が残っていないか。残っている場合は
   「この機能は設計できない」と明示し、対象外として進めるか決めてもらう。

## 進め方

### Step 1: 機能一覧の展開
要件定義書の機能一覧(F-xxx)を読み込み、機能ごとに処理概要を書く。
機能ID・画面ID・API ID・テーブルの対応表(トレーサビリティマトリクス)を必ず作る。
**この表が、タスク膨張を検知する最重要成果物。** 対応が取れないものは設計漏れ。

### Step 2: 画面設計
- 画面一覧: `SC-001` 形式のIDを振り、対応する機能ID・利用ロールを記載
- 画面遷移図: Mermaid `flowchart` で作成。ログイン前/後、ロール別に分ける
- 主要画面(トップ5画面程度)はワイヤーフレームの代わりに
  「表示項目一覧+入力項目一覧+バリデーション+アクション」の表で定義する
- 共通UI(ヘッダ、エラー表示、ローディング等)のルールを1セクションで定義

### Step 3: API設計
- API一覧: `API-001` 形式のID、メソッド、パス、対応機能ID
- REST規約(命名、ステータスコード、エラーレスポンス形式、ページネーション、認証ヘッダ)を先に決める
- 主要APIはリクエスト/レスポンスのJSON例まで書く
- 認証・認可方式(誰がどのAPIを呼べるか)をロール×API のマトリクスで書く

### Step 4: 処理方式設計
- 主要ユースケース(3〜5個)のシーケンス図を Mermaid `sequenceDiagram` で作成
- バッチ処理一覧(あれば): 起動条件、多重起動制御、リラン方法
- 外部システム連携(あれば): 連携方式、障害時のリトライ・整合性担保
- 非同期処理・通知(メール等)の方式

### Step 5: 共通設計
- エラーハンドリング方針(エラーコード体系)
- ログ設計(何を、どのレベルで、どこに出すか)
- タイムゾーン・日付の扱い、文字コード、ID採番方式

### Step 6: セルフレビュー
- [ ] 全機能IDが画面またはAPIに紐づいている(トレーサビリティ表で確認)
- [ ] 全画面から到達できない画面、どの画面からも呼ばれないAPIがないか
- [ ] エラー系(異常系)の画面・レスポンスが定義されているか
- [ ] 権限の抜け(一般ユーザーが管理APIを呼べる等)がないか
- [ ] Mermaid図が構文エラーなくレンダリングされるか

### Step 7: 提出と次工程の案内
次工程は `db-design`(DB設計)と `architecture-design`(アーキテクチャ設計)。
この2つは基本設計書のドラフトを見ながら並行で進められることを伝える。

## 禁止事項
- 要件定義書なしで書き始めること
- 「詳細は実装時に決める」を多用すること(基本設計で決めるべきことのリストを守る)
- 正常系だけ設計して異常系を省略すること

## コンテキスト管理(必須)

- **調査は委任する。** 既存コードの読み込みは `code-scout`、既存ドキュメントの読み込み・整合チェックは
  `doc-scout` サブエージェントに委任し、要約(出典つき)だけを受け取る。
  自分でReadしてよいのは「これから編集するファイル」と「委任結果で特定された数箇所の確認」のみ。
- **インプットは全文引用しない。** 参照は「ドキュメントID §セクション」で行う。
  必要な抜粋(機能一覧表など)だけをdoc-scoutに抽出させる。
- **成果物はファイルに書き、チャットには出さない。** docs/ に保存し、応答は
  「要点サマリ(15行以内)+保存パス+レビューしてほしい箇所」のみ。
- **レビューは `doc-reviewer` サブエージェントに委任**し、指摘表だけ受け取る。
- 長い工程の途中では、確定事項を docs/ 側に書き出してから次に進む
  (会話が切れても docs/ だけで再開できる状態を常に保つ)。

## ロジック委譲・チェックポイント(必須)

**AIでやらないこと(tools/のスクリプトを実行して結果だけ読む):**
- ID整合チェック: `python3 tools/check_traceability.py docs`(表の突き合わせを自分でやらない)
- Mermaid検証: `python3 tools/validate_mermaid.py docs`
- 納期・ベロシティ計算: `python3 tools/forecast.py ...`(計算はスクリプト、AIは入力値の決定と解釈のみ)
- ゲート判定: `python3 tools/check_gate.py`

**中断・再開プロトコル(コンテキスト切れ・停止への備え):**
1. 開始時: `python3 tools/pipeline.py status` を実行。この工程(design)が in_progress で
   docs/wip/ に継続メモがあれば、**最初からやり直さず**メモの「次の1手」から再開する
2. 開始宣言: `python3 tools/pipeline.py start design`
3. 主要Step完了ごとに: 成果物をdocsに保存 → `python3 tools/pipeline.py step design "StepN完了"` →
   docs/wip/design_継続メモ.md を上書き(済みStep / 確定事項 / 未解決の論点 / 次の1手 を各3行以内)
4. 完了時: `python3 tools/pipeline.py done design` を実行し、継続メモを削除する

この手順により、途中でセッションが止まっても /resume で数秒で復帰できる。

## 憲法の遵守(必須)

開始時に `docs/00_プロジェクト憲法.md` が存在すれば必ず読み、全出力をその原則に従わせる
(短い1ページなのでこれは自分で読んでよい)。憲法と矛盾する指示・要望を受けたら、
黙って従わず「憲法§Xと矛盾するため、先に憲法改訂(変更提案書=/change)が必要」と指摘する。
憲法が存在しない場合は、要件定義の完了時に templates/00 からドラフトを作ることを提案する。
