# アーキテクチャ設計スキル

要件定義書・非機能要件定義書をインプットとして、アーキテクチャ設計書を作成する。
テンプレートは `templates/07_アーキテクチャ設計書.md`。
論理構成(アプリの層構造)と物理構成(インフラ)の両方を扱う。

## 前提条件の確認
- 非機能要件(想定ユーザー数、可用性目標、予算)を確認する。なければ Step 0 として簡易ヒアリング:
  1. 同時利用ユーザー数と1年後の想定
  2. 停止が許されるか(業務時間内のみ稼働でよいか、24/365か)
  3. 月額インフラ予算の上限
  4. チームの運用スキル(コンテナ運用経験、IaC経験)
- クラウドは指定がなければAWSを既定とし、選定理由を書く。

## 進め方

### Step 1: アーキテクチャ方針の決定(ADR形式)
重要な選定は「選択肢比較表 + 決定 + 理由」のADR(Architecture Decision Record)形式で残す。
最低限決めるもの:
- アプリ実行基盤(例: ECS Fargate / Lambda / EC2 / App Runner)
- DB(例: RDS / Aurora / Aurora Serverless v2)
- フロント配信(例: S3+CloudFront / Amplify Hosting / SSRサーバ)
- 認証(例: Cognito / 自前実装 / Auth0)
- **小規模チーム(3人程度)の場合は「運用の手間が最小」を第一評価軸にする**

### Step 2: 論理アーキテクチャ図(Mermaid flowchart)
レイヤ構造(フロント / API / ドメイン / データ)と依存方向、
主要な外部サービス(メール送信、決済等)との関係を描く。

### Step 3: インフラ構成図(Mermaid flowchart + subgraph)
AWSの場合、以下を含める:
- VPC / サブネット構成(public / private)、Multi-AZの範囲
- 各コンポーネント(ALB, ECS, RDS, S3, CloudFront, Cognito, SES 等)と通信経路
- 本番 / ステージング / 開発 の環境一覧表(構成差分とアカウント分離方針)
- ※Mermaidで表現しきれない詳細は、draw.io(diagrams.net)用のAWSアイコン構成図を
  別途作ることを提案してよい(XMLエクスポートも可能)

### Step 4: 非機能の実現方式
非機能要件定義書の各項目に対し「どう実現するか」を対応表で書く:
- 可用性: Multi-AZ、ヘルスチェック、目標復旧時間(RTO/RPO)とバックアップ設計
- 性能: スケーリング方式(オートスケール条件)、CDN、キャッシュ
- セキュリティ: WAF、Secrets管理、IAM最小権限、通信・保存の暗号化、脆弱性スキャン
- 監視: メトリクス・ログ・アラートの一覧(何を監視し、閾値超過で誰に通知するか)

### Step 5: CI/CDとリリース設計
- パイプライン図(build → test → deploy)と使用サービス(GitHub Actions等)
- ブランチ戦略とデプロイフロー(誰が本番デプロイを承認するか)
- DBマイグレーションの適用手順とロールバック方針

### Step 6: コスト概算
主要リソースの月額概算表を作る(本番+ステージング)。
単価は変動するため「実施日時点の概算であり、AWS料金計算ツールでの再見積りを推奨」と明記する。
予算超過の場合は縮小案(例: Aurora→RDS single-AZ、Fargate→Lambda)を提示する。

### Step 7: セルフレビュー
- [ ] 非機能要件の全項目に実現方式が対応しているか(対応表で確認)
- [ ] 単一障害点(SPOF)が許容範囲か、明示されているか
- [ ] 3人チームで運用できる構成か(過剰にマイクロサービス化していないか)
- [ ] コスト概算が予算内か
- [ ] Mermaid図が構文エラーなくレンダリングされるか

## 禁止事項
- 選定理由のない技術選定(「流行っているから」はNG。比較表を必ず作る)
- チーム規模に対して過剰な構成(K8s、マイクロサービス等)を無条件に提案すること
- コスト概算の省略

## コンテキスト管理(必須)

- **調査は委任する。** 既存コードの読み込みは `code-scout`、既存ドキュメントの読み込み・整合チェックは
  `doc-scout` サブエージェントに委任し、要約(出典つき)だけを受け取る。
  自分でReadしてよいのは「これから編集するファイル」と「委任結果で特定された数箇所の確認」のみ。
- **インプットは全文引用しない。** 参照は「ドキュメントID §セクション」で行う。
  必要な抜粋(機能一覧表など)だけをdoc-scoutに抽出させる。
- **成果物はファイルに書き、チャットには出さない。** docs/ に保存し、応答は
  「要点サマリ(15行以内)+保存パス+レビューしてほしい箇所」のみ。
- **レビューは `doc-reviewer` サブエージェントに委任**し、指摘表だけ受け取る。
- 長い工程の途中では、確定事項を docs/ 側に書き出してから次に進む
  (会話が切れても docs/ だけで再開できる状態を常に保つ)。

## ロジック委譲・チェックポイント(必須)

**AIでやらないこと(tools/のスクリプトを実行して結果だけ読む):**
- ID整合チェック: `python3 tools/check_traceability.py docs`(表の突き合わせを自分でやらない)
- Mermaid検証: `python3 tools/validate_mermaid.py docs`
- 納期・ベロシティ計算: `python3 tools/forecast.py ...`(計算はスクリプト、AIは入力値の決定と解釈のみ)
- ゲート判定: `python3 tools/check_gate.py`

**中断・再開プロトコル(コンテキスト切れ・停止への備え):**
1. 開始時: `python3 tools/pipeline.py status` を実行。この工程(arch)が in_progress で
   docs/wip/ に継続メモがあれば、**最初からやり直さず**メモの「次の1手」から再開する
2. 開始宣言: `python3 tools/pipeline.py start arch`
3. 主要Step完了ごとに: 成果物をdocsに保存 → `python3 tools/pipeline.py step arch "StepN完了"` →
   docs/wip/arch_継続メモ.md を上書き(済みStep / 確定事項 / 未解決の論点 / 次の1手 を各3行以内)
4. 完了時: `python3 tools/pipeline.py done arch` を実行し、継続メモを削除する

この手順により、途中でセッションが止まっても /resume で数秒で復帰できる。

## 憲法の遵守(必須)

開始時に `docs/00_プロジェクト憲法.md` が存在すれば必ず読み、全出力をその原則に従わせる
(短い1ページなのでこれは自分で読んでよい)。憲法と矛盾する指示・要望を受けたら、
黙って従わず「憲法§Xと矛盾するため、先に憲法改訂(変更提案書=/change)が必要」と指摘する。
憲法が存在しない場合は、要件定義の完了時に templates/00 からドラフトを作ることを提案する。
