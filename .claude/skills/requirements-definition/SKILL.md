# 要件定義スキル

システム開発の要件定義書と非機能要件定義書を作成する。
テンプレートは `templates/01_要件定義書.md` と `templates/02_非機能要件定義書.md` を使う
(見つからない場合はこのスキル内の構成定義に従って生成する)。

## 進め方(必ずこの順で)

### Step 1: インプットの収集
まず以下を探す・確認する。あるものは全部読む。
- ユーザーストーリー、企画メモ、議事録、既存の要件メモ
- 既存コード(すでに開発が始まっている場合)— READMEとルーティング/画面一覧から現状機能を逆引きする
- 競合・類似サービスの情報(ユーザーが言及した場合)

### Step 2: ヒアリング(不足情報の質問)
以下が読み取れない場合、**ドラフトを書く前に**ユーザーに質問する。
一度に質問するのは最大5問。優先度順に:
1. **目的とKPI**: このシステムは誰のどんな課題を解決するか。成功をどう測るか
2. **利用者**: ユーザー種別(ロール)と想定人数・同時利用数
3. **スコープ境界**: 今回のリリースで「やらないこと」は何か
4. **納期と体制**: リリース希望日、開発メンバ数とスキルセット
5. **制約**: 予算、既存システム連携、法規制(個人情報等)

### Step 3: 要件定義書ドラフトの生成
テンプレートの全セクションを埋める。ルール:
- 機能要件は必ず `F-001` 形式のIDを振り、ユーザーストーリーとの対応表を作る
- **全ストーリーがどれかの機能IDに紐づいていること**を確認する(迷子ストーリー=後で膨らむタスクの温床)
- 各機能に優先度を付ける: `MUST`(ないとリリース不可) / `SHOULD`(重要) / `COULD`(余裕があれば) / `WON'T`(今回やらない)
- 決められない項目は `【未確定】理由と決定期限` と書く。勝手に決めない
- スコープ外(やらないこと)を最低5項目書く。書けない場合はユーザーに「やらないこと」を質問する

### Step 4: 非機能要件定義書の生成
IPA非機能要求グレードの6カテゴリ(可用性・性能/拡張性・運用/保守性・移行性・セキュリティ・環境/エコロジー)
に沿って `templates/02_非機能要件定義書.md` を埋める。
小規模チームの場合は「松竹梅」の3段階で提示し、ユーザーに選ばせる。

### Step 5: セルフレビュー
生成後、以下の観点で自分の出力を検査し、問題があれば修正してから提出する:
- [ ] 機能一覧とユーザーストーリー対応表に漏れがないか
- [ ] MUSTだけで最小リリースが成立するか(MUSTが多すぎないか — 全体の5割以下が目安)
- [ ] 「やらないこと」が具体的か(「頑張らない」のような曖昧表現はNG)
- [ ] 【未確定】項目がすべて課題一覧に転記されているか
- [ ] 用語集に載っていない業務用語を本文で使っていないか

### Step 6: 提出と次工程の案内
ドキュメントをユーザーに渡し、以下を伝える:
- レビューしてほしい箇所(特に判断が割れそうな優先度付け)
- 【未確定】項目の一覧と、それぞれ誰がいつまでに決めるべきか
- 承認後の次工程は基本設計(`basic-design` スキル)であること

## 禁止事項
- ヒアリングを省略して憶測で埋めること(憶測で埋めた場合は必ず【仮】マークを付ける)
- 非機能要件を「一般的な水準とする」で済ませること(数値目標を書く)
- スコープ外セクションを空のまま提出すること

## コンテキスト管理(必須)

- **調査は委任する。** 既存コードの読み込みは `code-scout`、既存ドキュメントの読み込み・整合チェックは
  `doc-scout` サブエージェントに委任し、要約(出典つき)だけを受け取る。
  自分でReadしてよいのは「これから編集するファイル」と「委任結果で特定された数箇所の確認」のみ。
- **インプットは全文引用しない。** 参照は「ドキュメントID §セクション」で行う。
  必要な抜粋(機能一覧表など)だけをdoc-scoutに抽出させる。
- **成果物はファイルに書き、チャットには出さない。** docs/ に保存し、応答は
  「要点サマリ(15行以内)+保存パス+レビューしてほしい箇所」のみ。
- **レビューは `doc-reviewer` サブエージェントに委任**し、指摘表だけ受け取る。
- 長い工程の途中では、確定事項を docs/ 側に書き出してから次に進む
  (会話が切れても docs/ だけで再開できる状態を常に保つ)。

## ロジック委譲・チェックポイント(必須)

**AIでやらないこと(tools/のスクリプトを実行して結果だけ読む):**
- ID整合チェック: `python3 tools/check_traceability.py docs`(表の突き合わせを自分でやらない)
- Mermaid検証: `python3 tools/validate_mermaid.py docs`
- 納期・ベロシティ計算: `python3 tools/forecast.py ...`(計算はスクリプト、AIは入力値の決定と解釈のみ)
- ゲート判定: `python3 tools/check_gate.py`

**中断・再開プロトコル(コンテキスト切れ・停止への備え):**
1. 開始時: `python3 tools/pipeline.py status` を実行。この工程(req)が in_progress で
   docs/wip/ に継続メモがあれば、**最初からやり直さず**メモの「次の1手」から再開する
2. 開始宣言: `python3 tools/pipeline.py start req`
3. 主要Step完了ごとに: 成果物をdocsに保存 → `python3 tools/pipeline.py step req "StepN完了"` →
   docs/wip/req_継続メモ.md を上書き(済みStep / 確定事項 / 未解決の論点 / 次の1手 を各3行以内)
4. 完了時: `python3 tools/pipeline.py done req` を実行し、継続メモを削除する

この手順により、途中でセッションが止まっても /resume で数秒で復帰できる。

## 憲法の遵守(必須)

開始時に `docs/00_プロジェクト憲法.md` が存在すれば必ず読み、全出力をその原則に従わせる
(短い1ページなのでこれは自分で読んでよい)。憲法と矛盾する指示・要望を受けたら、
黙って従わず「憲法§Xと矛盾するため、先に憲法改訂(変更提案書=/change)が必要」と指摘する。
憲法が存在しない場合は、要件定義の完了時に templates/00 からドラフトを作ることを提案する。
