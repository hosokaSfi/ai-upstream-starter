キット(プロセス)自体の改善を行います。インプット: $ARGUMENTS
(引数がなければ、直近のスプリント計画書§5・課題管理表・velocity.json から問題の兆候を拾う)

## 手順

1. **データで裏を取る**(AIの印象ではなく計測値から):
   - `python3 tools/forecast.py --accuracy --velocity-file docs/backlog/velocity.json`(計画過大/過小の傾向)
   - 課題管理表の期限切れ件数、変更提案書(docs/changes/)の件数と傾向
   - doc-scout に委任: 直近スプリントで「設計書に書いてなくて実装中に決めたこと」を洗い出す

2. **問題を「プロセスのどの層の欠陥か」に分類する**:
   - 憲法の原則が曖昧/欠けている → docs/00_プロジェクト憲法.md の改訂案
   - スキルの手順が実態に合っていない → .claude/skills/ の該当SKILL.mdの改訂案
   - 毎回同じ指摘が出る → hooks/tools のチェックに昇格する案
   - テンプレートに常に書かない欄がある → templates/ の削除・簡素化案

3. **改訂案を差分で提示し、人間の承認後に適用する**。1回の/kaizenで変えるのは
   **最大2箇所**(Tryを絞るのと同じ理由。一度に変えると効果が測れない)

4. 適用したら `docs/kaizen_log.md` に「日付 / 問題 / 変更箇所 / 効果測定方法」を追記し、
   次回の/kaizenで前回の変更が効いたかを最初に検証する

## 原則

- 計測に基づかない改訂はしない(「なんとなく手順を増やす」はプロセス肥大の始まり)
- ルールを増やす前に「既存ルールを削る・機械化する」選択肢を必ず検討する
- スキルの大規模な改修が必要な場合は skill-creator スキルの利用を提案する
